# 「导出修订后合同」功能实施计划书

> 状态：待评审 | 日期：2026-08-15 | 范围：contract 项目

---

## 1. 功能目标

审查完成后，用户在报告页逐条采纳/驳回修订建议，一键导出「采纳后」的修订后合同全文，让审查结果真正回写到原文、产出可用的新合同，形成闭环：

```
审查 → 修订建议 → 逐条决策(采纳/驳回/需律师) → 一键导出修订后合同
```

---

## 2. 现状调研结论（决定方案的关键事实）

### 2.1 数据资产

| 表 | 关键字段 | 说明 |
|---|---|---|
| `contract_reviews` | `filename`（upload 存储名）、`original_filename`、`status` | ⚠️ **未存原文 text** |
| `contract_clauses` | `clause_id`（**hash**）、`seq_no`、`title`、`content`、`char_start`、`char_end` | 条款已按 seq_no 排序，char 偏移相对原文 |
| `revision_accepts` | `clause_id`（**LLM 语义描述**）、`before_text`、`after_text`、`status` | after_text 已就绪，status 为 pending/accepted/rejected/needs_lawyer |

### 2.2 两个 P0 障碍（必须先解决，否则合并不了）

**障碍一：clause_id 两边对不上（致命）**

实测数据（review 53）：

```
contract_clauses.clause_id  →  'f467563d1dec3c7b'（hash，make_clause_id 生成）
revision_accepts.clause_id  →  '第二条' / '借款期限条款' / '1.1-1.2'（LLM 填的语义描述）
```

根因：`revision_writer._revise_single_clause` 返回的是 `entry.clause_id`（LLM 生成的），而不是传入 `clause` 的真实 `clause_id`（hash）。**两边完全对不上，无法通过 clause_id 把 revision 关联回 clause。**

**障碍二：原文 text 不落库**

`contract_reviews` 表只存文件名，原文全文每次运行时从 `uploads/contracts/{filename}` 重新提取。`char_start/char_end` 是相对「那次提取的 text」的偏移。要做原文定位替换，需要重新提取原文（存在偏移不一致风险）。

---

## 3. 总体方案

### 3.1 核心设计：状态机（不是 agent pipeline）

本功能核心动作是「用户决策 + 文本合并」，**不涉及 LLM 推理**，因此**不另起 LangGraph agent**，用状态机表达状态转换：

```
每条修订(revision) 子状态机：
  pending ──用户决策──→ accepted / rejected / needs_lawyer

整份合同(contract) 主状态机：
  decision_pending ──→ decision_in_progress ──→ decision_completed ──→ merged
      （默认）           （有部分已决策）          （全部已决策）        （已导出）
```

主状态字段 `merge_status` 加到 `contract_reviews` 表，可选；也可用「revision 全部非 pending」动态推导，减少迁移。

### 3.2 前置修复一：clause_id 对齐

| 步骤 | 内容 |
|---|---|
| 1 | 修改 `revision_writer._revise_single_clause`：返回的 `clause_id` 改为传入 `clause["clause_id"]`（真实 hash），不再信任 LLM 填的 clause_id |
| 2 | 历史数据修复脚本：对存量 `revision_accepts`，用 `before_text` 在 `contract_clauses.content` 里做前缀/包含匹配，反查真实 clause_id 并回填 |

### 3.3 前置修复二：原文来源

**推荐方案**：合并时从 `uploads/contracts/{filename}` 重新提取原文（复用 upload 接口已有的 pdfplumber/docx/txt 提取逻辑，抽成公共函数 `extract_text_from_file`）。

**备选方案**：给 `contract_reviews` 加 `original_text TEXT` 字段，上传时落库。更稳但需迁移 + 老数据回填。

### 3.4 合并算法（推荐：clauses 重建 + char 间隔还原）

主路径（不依赖原文精确定位，可靠性高）：

1. 按 `seq_no` 升序取 `contract_clauses`
2. 对每条 clause，查 `revision_accepts WHERE clause_id = ? AND status='accepted'`
   - 命中 → 用 `after_text` 作为该条款新文本
   - 未命中 → 保留 `content`
3. 用 `char_start/char_end` 的差值重建条款间的原始间隔（空白/换行），按 `title` + 正文结构拼接
4. 输出全文

降级路径（char 定位替换，可选增强，保留最多原始格式）：

1. 从 uploads 重新提取原文 text
2. 校验 `char_start/char_end` 偏移与原 text 一致（不一致则回退主路径）
3. 用 `after_text` 替换 `text[char_start:char_end]` 区间（保留区间首尾空白包裹）

### 3.5 输出格式

- **一期（轻量）**：纯文本 `.txt`，UTF-8，条款间保留空行
- **二期（增强）**：`python-docx` 生成 `.docx`，`title` 用标题样式、正文用正文样式，产品感更强

## 4. 接口设计

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/v1/contract/{id}/final-contract` | GET | 返回合并后的修订后合同全文（JSON 含 text + 采纳统计），鉴权复用现有 get_current_user + 所有权校验 |
| `/api/v1/contract/{id}/final-contract/download` | GET | 返回文件流（Content-Disposition 附件），前端触发浏览器下载 |

可选：返回里带 `merge_summary`（总修订数 / 已采纳 / 已驳回 / 未决策），供前端提示「还有 N 条未决策」。

## 5. 前端设计（不新建左侧导航页）

| 位置 | 改动 |
|---|---|
| 审查报告页（`ContractReviewView.vue`） | 修订卡片上方加蓝色主按钮「导出修订后合同」，区别于现有的「导出报告」（=打印） |
| 左侧「最近审查」列表 | 每个合同加状态小标签：🟡 待处理 / 🟢 已生成 / ⚪ 仅浏览 |
| 交互 | 点击导出 → 调 download 接口 → 浏览器下载文件；若存在未决策修订，先弹确认框提示数量 |

设计原则：入口靠近用户操作位置（决策在报告页做，导出也在报告页），不抽离成独立 agent 页面。

## 6. 实施步骤（5 阶段）

| 阶段 | 内容 | 产出 |
|---|---|---|
| P1 | 修复 clause_id 对齐（revision_writer + 历史数据回填脚本） | 新旧数据 clause_id 统一 |
| P2 | 抽公共文本提取函数 + 实现合并算法（主路径） | 后端 merge 逻辑 |
| P3 | 新增 final-contract 两个接口 + 鉴权 | 可 curl 验证 |
| P4 | 前端按钮 + 状态标签 + 下载交互 | 可点选导出 |
| P5 | 测试（含 clause_id 回填准确性、合并正确性）+ 二期 docx 增强 | 验收通过 |

---

## 7. 测试与验收标准

- **单元测试**：合并算法对「部分采纳 / 全部采纳 / 无采纳 / 全部驳回」四类场景，输出正确（采纳的用 after_text，其余保留原文）
- **clause_id 回填**：历史数据回填后，revision 与 clause 关联率 ≥ 95%（抽样核验）
- **端到端**：上传合同 → 审查 → 采纳 2 条 → 导出，正文中该 2 条已替换、其余未变
- **权限**：非所有者无法导出他人合同（403）
- **回归**：现有 test_multi_dim / test_graph_smoke 不回归

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 填的 clause_id 历史数据无法全部反查 | 部分老合同合并不了 | before_text 前缀匹配 + 无法匹配的标「需人工」；新数据从 P1 起已正确 |
| 重新提取原文与当初偏移不一致 | 降级路径定位错位 | 主路径不依赖原文；降级路径加偏移校验，不一致即回退 |
| after_text 与 before_text 结构差异大（LLM 改写过度） | 替换后上下文不连贯 | 合并后对含「未决策」的条款不替换，导出时提示用户核对 |
| 输出 .docx 格式复杂度 | 二期延期 | 一期先交付 .txt，docx 独立排期 |
