## 0. 一句话定位（开场备用）

> 我做的是一个**合同审查智能体**：内部已上线，给同事审租赁/采购/服务这类商业合同时用。核心思路是「**规则闸门拦确定性硬伤 → RAG 补真法条依据 → 人工门控把住可信关**」的 6 节点 LangGraph 流水线。我主导架构和后端，技术选型我拍板，前端和测试有同学配合。

## 2. 为什么这样设计（架构决策与理由）

**① 为什么是 6 节点流水线，而不是拆成多个 Agent？**
合同审查是**单业务、强状态、线性为主**的流程：parse→rule_check→review→retrieve→human_gate→revise。用 `StateGraph` 6 节点比拆独立 Agent 更可控、状态更清晰、易调试；并发需求只在 `review` 内部用 LangGraph `Send` fan-out（四维并发）解决，不必为此上多 Agent 编排。

**② 为什么规则闸门要前置？**
LLM 贵且慢，而「违约金 >30%」「试用期 >6 个月」这类**确定性违规用正则就能判**。让规则先拦，确定性项不进 LLM → 省 Token、降延迟、还把"硬伤漏检"风险从模型可靠性问题变成"规则写好没"的工程问题。

**③ 为什么混合检索而非纯向量？**
合同问法和法条是两套语言（口语 vs 法言法语）。Dense 抓语义、Sparse 抓关键词（"违约金""不可抗力"这种术语），`WeightedRanker(0.7/0.3)` 融合互补；再上 BGE-Reranker-v2-M3 交叉编码器精排 Top-15，硬截断 <0.30 低相关，杜绝噪声进上下文。

**④ 为什么加 HyDE / 多查询？**
口语化弱命中是纯检索的死穴。HyDE 让 LLM 先生成"假设法条文本"再检索， bridging 语义鸿沟；多查询拆分 + Round-Robin 合并保证每个子意图都有代表，避免全局排序饿死低分子意图。评测表明这是 recall@3 从 38%→75% 的关键增量。

**⑤ 为什么用 `interrupt()` 做 HITL，而不是业务层弹窗？**
`interrupt()` 是 LangGraph 图级暂停——状态落 checkpointer、图真正停住，resume 用 `Command(resume=...)` 把法务决策作为 payload 传回，**不是靠前端轮询假装暂停**。这样"暂停—恢复"是确定性的、可审计的，符合法律场景对"人工确认留痕"的硬要求。

**⑥ 为什么接北大法宝 MCP，且只高风险触发 + 失败降级？**
本地 `kb_case` 是 LLM 提炼的"裁判规则"（无真实案号），对抗不了"编案例"的幻觉。北大法宝有 1.7 亿+ 真实判例补"有案可依"。但它是**在线额度服务**（900 次试用），所以**仅 `level==高` 触发**控成本，中低走本地秒回；MCP 失败/超时静默降级，绝不中断主流程——这是"离线 RAG + 在线 MCP 混合检索"架构。

**⑦ 为什么全链路降级 + 多租户校验？**
法律工具"给错结论"代价极高，所以每个节点都有兜底（解析挂→正则切分、评审挂→单次综合、检索挂→人工核实、修订挂→占位）。统一三层兜底 `retry→降级→系统兜底`。安全上主动补多租户越权：JWT 解析身份贯通 10 个核心接口所有权校验，阻断用户 A 读用户 B 合同。

## 3. 项目亮点（简历/口述高频抓手）

1. **规则闸门零成本前置**：40 条确定性规则（原 27 + 租赁/买卖/服务专项 13 条）毫秒级拦截确定性合规项，LLM 只干语义活——成本与可靠性双赢。
2. **检索管线有量化提升**：BGE-M3 混合 + Reranker + HyDE，口语化 recall@3 38%→75%（技术评测指标，非业务效果）。
3. **图级 HITL 人工门控**：`interrupt()/Command(resume)` 实现真暂停—恢复闭环，法律场景可审计、留痕。
4. **真实落地 MCP 混合检索**：离线 RAG + 在线北大法宝 MCP，高风险补真实案号判例抗幻觉，失败静默降级。
5. **全链路可降级 + 数据隔离**：三层兜底 + 10 接口多租户所有权校验，工程可靠性到位。
6. **不是 demo**：235 个 pytest 用例 + 检索质量评测脚本（黄金集 recall/MRR），单测与评测覆盖。

## 4. 团队是怎么样的（怎么表达才真实）

**真实情况**：你**主导**这个项目——审查 Agent 的整体架构、后端（LangGraph 流水线 / RAG 检索 / HITL 门控 / MCP 接入）由你负责，**技术选型你拍板**；前端有同学配合做 `HumanReviewPanel` 这类交互界面，测试/产品给需求反馈和用例协作。

**标准表达（不夸大、不缩水）**：
> "这个项目是我主导的，整体架构和后端都是我搭的，技术选型我来定。前端同学配合做人工复核面板那块交互，测试和产运同学给需求反馈、一起补用例。核心的检索管线和人工门控是我自己啃下来的。"

**避坑**：
- 别说"我一个人做完"——你说了有协作，前后矛盾会被抓。
- 也别说"我们团队做了"含糊带过——面试官要听**你**的贡献边界。明确"架构+后端是我，前端/测试协作"。
- 被问"前端是你写的吗"→ 诚实："复核面板的交互是前端同学做的，我定义接口和数据结构、串起 HITL 状态"。

## 5. 高频面试问题 + 标准回答（含追问）

**Q1. 为什么不直接用 LLM 审合同，要搞这么复杂？**
> 纯 LLM 两个致命问题：编法条编案例（法务不敢信）、确定性硬伤会漏。我用规则闸门兜确定性项、RAG 兜法条依据、人工门控兜最后可信关，把"可靠性"从模型能力问题拆成多层工程问题。

**Q2. 40 条规则里最难的是哪条？**
> 违约金抽取。要区分"违约金 35%"该拦、"违约金不超过 30%"不能拦——靠正则同时抽百分比和固定金额，再跟 30% 阈值比较，不是简单关键词匹配。（详见 `rule_engine.py` R 系列规则）

**Q3. recall@3 38%→75% 是什么口径？**
> 口语化子集（4 题）的 recall@3；38% 是 T0 基线，75% 是加 HyDE 后的值；测试集是 20 题法律黄金集，书面语稳定 100%。**这是技术评测指标，不是业务效果**。

**Q4. HyDE 触发阈值为什么是 0.80？**
> 硬截断已滤掉 <0.30 的命中，"top<0.3 触发"会永远不触发；0.80 落在口语化弱命中（≤0.79）与强命中（≥0.91）之间的空档，只对"检索到但不确定"的弱命中二次增强。

**Q5. interrupt 之后状态存哪、怎么恢复？**
> `MemorySaver` checkpointer + `thread_id`（`contract_{id}_run_1`）落状态；resume 用 `Command(resume=...)` 把法务决策作为 payload 传回 `wait_human_node`。图路径真暂停，另有直跑路径做逃生舱。

**Q6. 为什么是 6 节点不是多 Agent？**
> 单业务流水线用 StateGraph 比多 Agent 更可控、状态更清晰；并发只在 review 内用 Send fan-out 解决，不必为多并发上多 Agent 编排。（见 §2①）

**Q7. 北大法宝 MCP 挂了怎么办？**
> 静默降级：`search_cases` 返回空，流水线照常走本地 `kb_case`，绝不中断；且只有高风险触发，额度可控。

**Q8. 多租户怎么保证数据隔离？**
> JWT 解析用户身份，贯通 10 个核心接口的所有权校验（`_check_ownership`），阻断越权读他人合同。

**Q9. 并发评审怎么实现的？**
> `review` 节点内对 legal/compliance/financial/rights_obligations 四维度用 LangGraph `Send` fan-out 并发调用 LLM，结果汇聚后进入下一节点。

**Q10. 实时进度怎么做的？**
> 后端 SSE 流式推送各节点状态，前端进度条平滑展示；asyncio 全链路异步支撑并发与流式。

**Q11. 知识库怎么建的？**
> 四类：民法典（`civil_code_hybrid`）/ 司法解释（`kb_law`）/ 裁判规则（`kb_case`）/ 示范条款（`kb_template`），由 `scripts/` 脚本导入 Milvus；判例侧离线 `kb_case` + 在线北大法宝 MCP 混合。

**Q12. 如果重做，你会改什么？**
> 检索侧会加查询缓存降本；HITL 会做"批量确认"提升法务吞吐；MCP 触发可改成语义路由而非仅按风险等级。整体架构会保留。

**Q13. 上线后真实效果如何？**
> 内部已上线自用，同事审合同在用。量化上检索召回有提升（见 §6 口径）；**业务提效数字我没做系统性 A/B，不会编**。架构全链路可降级、有单测和评测脚本覆盖，这是我敢说"不是 demo"的底气。

**Q14. 你这个项目是 Agent 还是 Workflow？有没有参考过别的 RAG 架构？**
> 主体是**确定性工作流**——6 节点控制流写死、可审计、可复现，契合法律"零幻觉/留痕"硬要求；只有 HITL 人工闭环 + MCP 条件触发是 agentic 的，所以准确叫 **agentic workflow**，不是完全自主 Agent。我研究过业界一些 RAG 路由架构（确定性 DAG + 检索后置信度二次路由 + 对话记忆），骨架和我的判断一致，是我后续演进方向；但它两处兜底——web 搜索兜底、低置信裸生成——在法律场景是禁区（来源不可控 / 纯幻觉），我没抄，低置信兜底我用"承认不确定 + 转 HITL + 补北大法宝 MCP"替代。

**Q15. 你的 QA 意图识别为什么用纯规则（正则）不用 LLM 分类？**
> 合同 QA 域封闭（就问条款 / 审查结果 / 法律 / 闲聊几类），正则毫秒级、零成本、可解释可测；且我故意把默认路由设成 LAW、非 LAW 规则写得窄——宁可多检索一次，不能漏引法条。这套窄规则是被 eval 探针（"风险词注入假引用"）逼出来的，不是拍脑袋。换成 LLM 分类会多一次调用、结果不可复现，和法律"可审计"冲突。长尾混合意图是已知局限，演进方向是"正则为主 + 模糊时轻量 LLM 兜底"。

- 先给"三道防线"框架，再按模块展开；被深挖从**检索**或 **interrupt 恢复**切入（准备最足）。
